# ADR: M5.5 standalone linear recovery

- **Status: Accepted**
- **Scope:** planned M5.5 standalone runs only; it does not alter shipped M5 sequential-child behavior
- **Decision date:** 2026-08-29

## Context

A standalone Tau task can leave useful edits, completed investigation, tool
results, and verification-relevant facts behind when a provider or process fails
(or when Pi settles without a final `yield`). Starting again wastes that already
paid inference. The short-term objective is narrower than making an agent more
capable: settle objectively completed work, or continue the latest failed state
once, without fabricating a task graph or retaining a transcript.

The active M5.5 contract already calls for engine settlement, passive bounded
visible Pi JSON continuation state, factual run status, and run-ID recovery.
M5 is different: it owns one explicit parent-to-child edge, a child spec,
bounded handoff, and provider continuation. Its `--resume <edge-id>` remains an
edge operation. It is not the M5.5 public recovery operation and must not be
repurposed to represent a retry.

## Decision

M5.5 adds one local recovery lineage for a standalone run:

1. At a terminal session boundary, the engine may settle work without a model
   `yield` only when engine-observed finalization/integration, artifact-policy
   acceptance, and verification all pass. It performs no further model prompt
   to obtain a yield. A receipt identifies this as `engine_derived`; model
   `summary` and `deviations` are `unavailable`, not invented.
2. The session adapter passively observes Pi's **visible JSON** event stream and
   maintains a typed, deterministically compiled continuation record. It never
   asks the model to summarize, checkpoint, explain, or correct itself.
3. `status <run-id>` and `resume <run-id>` are run operations. Resume atomically
   claims the latest eligible failed record in the requested recovery lineage,
   restores the one latest opaque workspace continuation, injects the bounded
   record and typed failure evidence under the original task authority, and
   opens a new logical model/provider session.

This is the smallest mechanism that can avoid repeated investigation after a
failed standalone attempt. It is not a general recovery substrate.

## Lifecycle and linear claim semantics

A normal run captures visible candidate state while it executes. On a terminal
outcome:

- An accepted explicit `yield` follows the existing success path. A successful
  run has no recovery eligibility; temporary continuation state is deleted once
  normal durable evidence is delivered.
- A settled session without yield enters engine settlement. If every objective
  gate passes, it ships as engine-derived success. If a gate fails, the engine
  records the actual failure and may retain recovery state.
- A provider/process/tool/budget/verification failure preserves only a valid
  latest workspace continuation and compiled record, then becomes `failed`,
  `resumable`, or `blocked` as the facts require.
- Explicit worker rejection and explicit user cancellation are non-ship and are
  never converted to engine settlement. Cancellation also never causes an
  automatic resume.

The recovery ledger records only run identity, immutable task/spec identity,
predecessor/successor run identity, lifecycle phase, claim state, timestamps,
provider/config compatibility identities, local-record identity, and factual
blocker code. A conditional, durable claim is the single ownership decision:

- Resolve an input run ID to the terminal latest failed member of its recovery
  lineage. If it is eligible, compare-and-set it from `resumable` to `claimed`
  and allocate exactly one `successor_run_id`.
- Concurrent callers have one winner. Losers receive factual status (`claimed`,
  `successor_run_id`, or a blocker), and create neither a session nor a
  workspace.
- The claimed run is no longer eligible. If its successor fails, that successor
  is the next latest failed state; resolving the original run ID reaches that
  state. There is never more than one direct successor per failed run.
- A successor is a new standalone execution identity with `recovery_of_run_id`
  lineage metadata, not a child task. It creates no `task_edges` row, does not
  use a child ordinal or relationship, and emits no child lifecycle event.

Thus a retry is a line, not a fake child edge, tree, or DAG. Status reports only
facts: requested/run-lineage identity, latest failed run ID, lifecycle phase,
verification state, `resume_allowed`, `blocked_reason`, existing claim or
successor ID, record identity/version, and workspace-continuation availability.
It does not recommend a strategy or claim that a resume will succeed.

## Capability ownership and persistence boundaries

| Concern | Owner and boundary |
| --- | --- |
| Settlement, eligibility, claim, task authority, caps, and acceptance | Kernel. It decides only from typed workspace, artifact-policy, verification, and lifecycle facts. |
| Pi event observation | Session adapter at the Pi boundary. It passively receives visible JSON events and exposes no private-thought fields to Tau. |
| Record compilation and pruning | Deterministic kernel compiler. It makes no model call and cannot create instructions. |
| Continuation bodies | Typed local continuation store, outside the checkout and outside canonical artifacts. It holds the compiled body, selected visible entries, and the opaque workspace-continuation body. |
| Ledger | Run/lifecycle identities and references only; it does not contain Pi message bodies, tool bodies, transcript content, hidden reasoning, or opaque continuation bodies. |
| Workspace state | The configured workspace provider preserves, validates, and restores one opaque latest continuation. The kernel never interprets its token, revision, VCS ref, path, or branch. |
| Verification and delivery | Existing engine-owned verification, acceptance, receipt, trace, and delivery owners. |
| Status/resume surface | Interface adapter; it authorizes and renders kernel facts but does not decide eligibility. |

The local store is typed and local-user-state protected, with atomic writes and
content/length validation. Pi persistence is preferred when it can expose the
necessary visible JSON state and meet the declared schema, privacy, retention,
compatibility, and deterministic-cap requirements. Otherwise Tau uses the
smallest append-only local record store with equivalent validation. Neither
choice creates a general event log: records are only per-run recovery inputs,
not an event-sourcing source of task truth.

Provider-native session resume is an optional optimization, not authority. The
kernel first validates and bounds its own record, task authority, failure facts,
and workspace continuation, then always creates a new logical Tau session. A
provider may rehydrate/cache a compatible Pi session only as an implementation
of that new session. If Pi persistence is absent, corrupt, incompatible, or
unavailable, Tau starts the new session from its validated bounded record; it
never treats an opaque provider conversation as proof of what to resume.

## Record contents, privacy, and boundedness

The compiler has a versioned input/output schema and accepts only:

- the immutable validated task/spec and artifact-policy authority (or its typed
  reference), which is mandatory and cannot be pruned or overridden;
- selected **complete** visible Pi tool-call/result pairs, preserving the call
  ID and terminal result (including a typed error result) as one unit;
- latest provider-reported workspace/work-state identity and one opaque
  continuation-store reference;
- selected recent visible task context and existing bounded context/checkpoint
  references; and
- typed engine failure and verification evidence.

Visible entries are retained mechanically, not semantically summarized or
ranked for advice. The compiler excludes Pi thinking/private-reasoning fields,
hidden messages, compaction internals, unpaired tool calls/results, raw command
output that exceeds the store's safety policy, credentials, host paths, and
observability-only chatter. A sensitive or unsafe pair is omitted as a whole;
it is never retained partially. This preserves the complete tool-call/result
pairing invariant for every retained pair while allowing privacy policy to
remove a pair.

All limits are versioned configuration identities and are enforced twice: when
admitting an event and when writing/reading a record. The record declares its
UTF-8 byte cap, deterministic token estimate/cap, entry/pair cap, per-entry
cap, and expiry. Pruning has this fixed order:

1. reject a record that cannot retain task authority, required latest workspace
   identity, and typed failure evidence within the hard caps;
2. remove observability-only events, then oldest eligible visible chat/context;
3. remove complete optional tool pairs oldest-first, never splitting a pair;
4. retain the newest eligible state only if all byte and token caps still hold.

Selection ties use stable event sequence then call ID, never wall-clock timing
or model judgment. A record that still cannot meet both caps is not truncated
into an invalid recovery input: it is deleted/marked blocked with a stable
`continuation_over_budget` reason. This is intentionally a recovery blocker,
not an invitation to add arbitrary checkpoints.

Records expire at their declared expiry and are pruned deterministically by
expiry, then terminal successful settlement, then superseded/consumed lineage
state. Pruning deletes the local body and makes the ledger reference
non-resumable; it never deletes canonical receipts/traces or provider-owned
preserved work outside the provider's own policy. Missing, hash/length-invalid,
malformed, sensitivity-disallowed, expired, or schema/engine/Pi/provider
incompatible state fails closed before workspace restore or session spawn, with
respectively stable factual blocker categories such as `continuation_missing`,
`continuation_corrupt`, `continuation_expired`, or
`continuation_incompatible`.

Continuation data stays in local user state with restrictive permissions and is
never placed in the checkout, canonical trace, receipt, portable handoff,
benchmark artifact, or public status payload. It is operational recovery data,
not retained hidden reasoning. Existing M4 checkpoints remain structured
working state; they are not an alternate M5.5 transcript store.

## Failure and settlement semantics

Engine settlement is conservative. It is allowed only after the session has
actually settled, no explicit rejection/cancellation is recorded, the
engine-owned workspace finalizer has produced preserved work, integration is
clean, artifact policy accepts the integrated tree, verification passes, and
required durable delivery evidence can be completed. Any uncertainty is a
non-ship failure or delivery-pending fact, never a guessed success. A delivery
retry may replay already durable evidence but may not prompt the model again.

On a resumable failure, validation occurs before claim and again after claim
before model spawn: task/spec authority must match, the local record must pass
schema/hash/caps/expiry checks, the workspace provider capability identity and
opaque target must validate read-only, and the stored workspace revision must
match the record. Failure at either point leaves a truthful blocked outcome and
no successor session. Only the provider restores the workspace after the claim.

Successful runs receive **zero additional model turns and zero additional
inference tokens** from M5.5. Passive capture, deterministic compilation,
workspace/provider calls, verification, and artifact delivery are not model
inference. Resume input is paid only when a user/automation explicitly invokes
resume; no background retry exists.

## Compatibility and reconciliation

The recovery record schema, compiler version, cap-policy identity, Pi visible
JSON compatibility identity, engine version range, workspace capability
identity/version, and task/spec identity are stored with each record. Readers
may accept an explicitly supported older additive version; they must not migrate
by replaying or reinterpreting arbitrary Pi history. Unsupported versions block
rather than silently drop authority or manufacture state.

There is no active M5.5 product-scope conflict: the active product and
subsystem contracts expressly define this planned run-ID mechanism and keep it
separate from M5 edge resume. There is, however, an implementation boundary to
preserve: the shipped M5 ledger stores opaque continuation tokens and terminal
payloads for its hardened sequential-child protocol. That existing M5 contract
continues unchanged. M5.5 must neither reuse nor widen those rows; its new
standalone recovery ledger stores references/lifecycle facts only and its bodies
live in the local typed store. Treating an M5 edge as a recovery lineage would
break both contracts, so it is explicitly prohibited.

## Consequences

Standalone failures can continue with already observed, bounded factual state,
while objective no-yield success does not become manual recovery. The cost is a
small typed local store, explicit compatibility/retention policy, and several
fail-closed outcomes. The design deliberately does not promise to repair a bad
plan: a resumed worker can repeat its strategy or fail again.

### Rejected alternatives

- **Fake child edges:** falsely claim a new child task and contaminate M5 parent/
  child receipts, handoffs, and lifecycle semantics.
- **Branching/fan-out or multiple successors:** makes ownership, workspace
  authority, retention, and user intent non-linear.
- **Arbitrary checkpoints or historical workspace snapshots:** expands provider
  storage and selection semantics beyond the one latest state.
- **Corrective instruction overlays:** changes the user's task authority and
  smuggles strategy recovery into resume.
- **Semantic memory or strategy recovery:** requires interpretation, retention,
  and evaluation not justified by this short-term failure class.
- **Hidden reasoning retention:** is neither needed nor permitted.
- **Generalized recovery infrastructure/event sourcing:** creates permanent
  machinery before evidence shows that this narrow line is insufficient.

## Narrow implementation seams and sequencing

1. Define the versioned recovery record, local-store capability, retention
   policy, blocker/status vocabulary, and ledger identity/lifecycle references.
2. Add passive Pi-visible-JSON capture plus deterministic compilation and
   complete-pair/privacy/cap validation; exercise deletion and corrupt-store
   paths.
3. Add the terminal decision point: conservative engine settlement, latest
   workspace preservation, and failed-state publication, without changing M5
   child composition.
4. Add factual status and atomic linear run-ID claim/resume over the existing
   provider-neutral workspace continuation capability; native Pi resume remains
   optional behind the adapter.
5. Add close/reopen, concurrent-claim, expiry/pruning, incompatible/corrupt,
   cancellation/rejection, no-yield settlement, and no-extra-successful-
   inference conformance evidence before exposing the normal surface.

These are ownership seams and order of proof, not a prescription for files,
classes, database layout, or provider-specific code.

## Exit evidence

M5.5 is complete only when hermetic close/reopen evidence and bounded real
standalone dogfood show all of the following:

- accepted integrated work safely settles when Pi omitted `yield`, with an
  engine-derived receipt and no invented model summary;
- a transient standalone process/provider failure resumes by run ID into the
  latest preserved opaque workspace and bounded continuation state;
- the resumed worker demonstrably avoids repeating investigation retained in
  selected complete tool-call/result pairs;
- deterministic pruning preserves task authority and complete retained pairs,
  obeys byte/token/expiry caps, and blocks unfit state;
- corrupt, missing, expired, or incompatible data reports
  `resume_allowed=false` and a stable `blocked_reason` before session spawn;
- concurrent requests create one successor only, M5 child edges remain absent,
  and provider-native resume failure falls back or blocks truthfully; and
- successful runs add no model turns or inference tokens, while no resume occurs
  without an explicit request.
