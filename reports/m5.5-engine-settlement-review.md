# M5.5 engine-owned settlement review

## Executive Verdict: BLOCK

This review covers **milestone 2 only**: standalone no-yield settlement through the existing CLI/`runIsolatedTask`/`runParallelTask(singleTask=true)` path. It does not review or propose continuation/resume work, and no implementation fixes were made.

The settlement idea is directionally conservative and the happy path is proven, but the current commit is not safe to retain as milestone 2. Two failure boundaries can leave objective settlement without reconciliation or can publish contradictory terminal authority. Cancellation/rejection coverage and the required branch evidence are also incomplete.

- Reviewed ADR `docs/adr/m5.5-linear-recovery.md`, especially the non-ship cancellation/rejection rule (58-60), conservative settlement gates (172-180), and required conformance evidence (245-253, 268-276).

## Actual CLI path traced

1. CLI strict-parses the spec/policy, creates the attempt trace, and calls `runIsolatedTask` (`src/cli.ts`); the isolated adapter supplies one spec, `singleTask: true`, and forwards events (`src/daemon/isolated.ts:41-56`).
2. `runParallelTask` validates task-base capabilities before provisioning, allocates the attempt/task identity, records queued/executing ledger state, acquires context, prepares an AI integration base, creates the workspace, and inserts the worker session (`src/daemon/parallel.ts:240-350`, `:566-650`).
3. It spawns the host, attaches watchdogs, and runs the prompt. It then collects provider usage, closes the handles, and derives the interruption (`:734-795`). A deferred interruption is returned before finalization only for the retained M5 sequential-child composition (`:773-795`).
4. Otherwise it finalizes each worker (`:798-824`). A resolved prompt with no yield, no watchdog abort, a task-base base, and a non-undefined finalization becomes an engine candidate (`:826-842`). The worker receipt is `ship`, uses finalizer paths/commit identity, records the session as `exhausted`, and sets no model yield payload (`:877-894`).
5. Healthy contexts are atomically combined. Conflicts become `escalate` and preserve/reconcile work (`:1067-1158`). A clean combine is materialized into the main checkout and verified once through the environment driver (`:1161-1191`).
6. The acceptance gate consumes combine/finalizer paths, present/deleted evidence, the integrated-change flag, combine commit, and verification result (`:1193-1236`). On rejection or verification/worker failure it writes a failure artifact, marks workspaces orphaned, calls the post-mortem, marks the aggregate failed, and emits `task.failed` (`:1257-1315`). On success it calls `onAccepted`, cleans healthy workspaces, marks tasks completed, records routing feedback, and emits `task.completed` with `settlementSource` (`:1318-1350`).
7. CLI delivery first writes a failed provisional receipt, records receipt delivery, writes/re-writes the trace, and only then attempts the shipped receipt rewrite (`src/cli.ts:908-1058`). The trace projection preserves session outcome and settlement source (`src/cli.ts:424-496`, `contracts/trace.ts:397-431`). This ordering is sensible for files, but the runner has already emitted/completed the ledger task before this external delivery fence.

## Findings (prioritized)

### C1 — Uncaught materialization/verification failures bypass failure hygiene

`taskBase.materialize()` and `verifyThroughEnvironment()` are called outside the settlement `try/catch` (`parallel.ts:1161-1173`). A materialization error or a provider/environment exception leaves the task in `verifying` and skips the failure artifact, `reconcileFailedRun`, terminal task state, and useful-work preservation. This was reproduced with an adversarial driver: the call threw `Error: materialize fault`, and the ledger task remained `verifying`.

The same failure mode applies to malformed fulfilled finalizer evidence before the acceptance stage. This violates the ADR's fail-closed settlement and R6's requirement that reconciliation occur after objective settlement failure.

**Smallest closure action:** put materialization, verification, and runtime evidence validation inside one terminal failure fence that records the factual cause, invokes reconciliation exactly once, and marks the task/workspaces non-ship. Add throw/malformed-evidence regression tests.

### C1 — Standalone external delivery can contradict durable completion

The runner sets the task completed and emits `task.completed` before CLI receipt/trace delivery (`parallel.ts:1318-1350`). CLI delivery failures only update a sequential child outbox; for standalone runs `acknowledgeExternal` returns true without ledger mutation (`cli.ts:919`, `:968`). Thus a failed receipt or trace can return a failed CLI result while the ledger remains completed and the trace already contains a successful terminal event.

**Smallest closure action:** make delivery a required durable settlement stage for standalone runs too, with a once-only `delivery_pending`/failed durable state (or delay the authoritative completed transition until receipt and trace are durably acknowledged). Ensure the canonical trace/task event cannot claim shipment before that fence.

### C1 — Settle watchdog race can defeat the no-yield decision and add inference

The existing settle watchdog nudges on the first no-yield `settled` event and aborts only on a later no-yield settlement (`guards/watchdog-driver.ts:213-225`, `:300-327`). `runParallelTask` does not await that nudge before reading the candidate and finalizing (`parallel.ts:734-842`). A real provider can therefore be engine-shipped during the nudge window, or spend another model turn/tokens after the purported terminal boundary.

**Smallest closure action:** define one ownership rule: either settle engine-owned no-yield only after the watchdog is conclusively disposed without a nudge, or bypass the settle nudge for this lane. Add a delayed-nudge regression that proves no extra prompt/turn and no shipment after an abort.

### C2 — Cancellation/rejection is not a first-class settlement fact

The only candidate exclusions are a rejected prompt and an observed watchdog abort. There is no user `AbortSignal`, explicit rejection event, or cancellation fact in the standalone runner/CLI contract. A host that resolves `prompt()` after an external abort or refusal can satisfy the candidate predicate. This is especially concerning because the ADR explicitly requires both explicit worker rejection and user cancellation to remain non-ship.

**Smallest closure action:** carry a typed terminal disposition (`settled`, `rejected`, `cancelled`, `watchdog-aborted`) from the host through the runner and require exactly `settled` for engine settlement; wire the CLI cancellation boundary to it. Do not infer disposition from a missing yield or error text.

### C2 — Runtime acceptance authority is structurally typed but not runtime-validated

`WorkspaceFinalization` and `CombineOutcome` are TypeScript interfaces, while the settlement decision trusts a non-undefined finalizer and provider-returned strings/arrays. Acceptance normalizes paths but does not validate the finalization/combine object, commit identity shape, or consistency between `hasChanges` and returned paths. This leaves schema drift and duplicate authority at the provider boundary even though the pure acceptance tests are strong.

**Smallest closure action:** add strict runtime schemas for provider evidence and validate them before deriving receipts/candidates; make the combine commit and integrated path set the sole aggregate authority, with finalizer data used only in its defined per-worker role.

The new successful no-yield test is a genuine pre-change regression: before the settlement delta, the no-yield branch could not produce the engine-derived shipped receipt (`test-parallel.ts:571-618` versus the changed candidate/receipt logic). However, the suite does not pin throwing materialization/verification, malformed finalization, cancellation/refusal, settle-nudge races, no-yield conflict, full-pipeline policy rejection/no-change, or standalone CLI delivery failure. The green suite therefore does not establish readiness.

## What is sound and should be retained

- Engine authority is explicitly named and additive (`contracts/settlement.ts:11-48`); engine-derived settlement has no `Yield`, summary, or deviations.
- Engine receipts use observed turns and measured usage, not invented model fields (`parallel.ts:877-894`; `test-parallel.ts:604-612`).
- Model-yield paths remain the compatibility default, and M5 sequential-child behavior remains covered by `test-sequential.ts`; the retained-child interruption fast path is intentionally before ordinary settlement (`parallel.ts:773-795`).
- Provider finalization and combine evidence replace model commit/path claims for the engine lane; acceptance checks required/present/deleted paths, change state, verification, and commit identity (`acceptance.ts:129-225`).
- Trace projection preserves `settlementSource`, and the observed session event ordering is yield-before-settle at the host (`sessions/host.ts:419-429`; `contracts/trace.ts:397-431`).
- Ordinary caught merge/conflict/acceptance/verification-result failures defer reconciliation until after the objective gate fails, and each such path calls `reconcileFailedRun` once (`parallel.ts:1037-1061`, `:1067-1087`, `:1257-1315`). Useful work is preserved by the provider post-mortem when those paths are reached.

## Closure decision

Do not retain the current commit as milestone 2. The smallest closure is not a continuation/resume expansion: close the terminal failure fence around materialization/verification/evidence validation, make standalone delivery part of the durable settlement fence, and carry typed cancellation/rejection plus the settle-watchdog decision through that fence. Then add the focused regressions listed under C3 and rerun the same commands. Re-review milestone 2 only after those facts are demonstrated.
